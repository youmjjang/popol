HTTP Status Pattern Analyzer.

HTTP 오류 유형에 따라 분석 기준을 나누고, 판단 근거를 확인할 수 있도록 개선했습니다.

처음에는 4xx 오류 전체에 같은 시간창과 반복 횟수 기준을 적용했습니다. 하지만 인증 실패와 없는 페이지 요청은 발생 원인이 다른데도 같은 기준으로 경보가 발생해, 어떤 요청을 먼저 확인해야 하는지 구분하기 어려웠습니다. 이를 개선하기 위해 오류 유형별로 기준을 비교하고, 선택한 규칙을 Windows 로그 분석 앱에 반영했습니다.

Python · 실험 분석C# · Windows Forms슬라이딩 시간창모의실험 48조건CSV · JSON

오류의 차이를 구분하기 어려웠습니다.

02 / PROBLEM SOLVING

만들면서 마주친 문제를
이렇게 해결했습니다.

오류를 묶는 기준, 분석 결과를 보여주는 방식, 입력 로그 처리에서 발견한 문제를 수정했습니다.

CASE 01 PROBLEM → CHANGE → RESULT

오류 유형별로 기준을 나눴습니다

문제

4xx 전체에 같은 기준을 적용하면 인증 실패와 없는 페이지 요청, 요청 제한이 같은 방식으로 처리됐습니다. 오류의 의미와 반복 패턴을 구분할 필요가 있었습니다.

수정 과정

401/403·404·429·5xx로 나누고, 30·60·120초의 시간창과 3·5·8·12회의 반복 횟수를 조합해 총 48개 조건을 비교했습니다. 오탐만 줄이는 대신 탐지된 이상 사례와 놓친 사례도 함께 확인했습니다.

결과

기존 모의실험 결과를 재집계한 비교에서 공통 기준 대비 오탐은 117건에서 25건으로 줄고, F1은 0.904에서 0.949로 높아졌습니다. 미탐은 44건에서 55건으로 늘어 두 결과를 함께 기록했습니다. 유형별로 선택한 기준은 앱의 기본 분석 규칙에 반영했습니다.

CASE 02 PROBLEM → CHANGE → RESULT

숫자 옆에 판단 이유와 원본 로그를 붙였습니다

문제

초기 화면은 Host/IP와 발생 횟수, 임계값을 중심으로 보여줘 경보가 발생한 이유를 확인하려면 원본 로그를 다시 찾아야 했습니다.

수정 과정

어떤 경로에서 어떤 오류가 몇 초 동안 반복됐는지 문장으로 설명하도록 바꿨습니다. 판단에 사용한 원본 로그와 주요 경로도 같은 화면에서 확인할 수 있도록 연결했습니다.

결과

분석 결과에서 확인 대상을 고른 뒤, 반복 패턴과 원본 로그를 따라가며 판단 근거를 확인할 수 있도록 개선했습니다.

CASE 03 PROBLEM → CHANGE → RESULT

잘못된 줄이 섞여도 유효한 로그는 분석하도록 했습니다

문제

로그 형식이 다르거나 일부 줄이 손상된 경우에도 분석할 수 있어야 했습니다. 정해진 예제 하나만으로는 입력 처리가 올바른지 확인하기 어려웠습니다.

수정 과정

Nginx/Apache 로그와 CSV·JSON·JSONL을 처리하고, 형식이 다른 동일 데이터와 잘못된 줄이 섞인 입력을 비교했습니다. 역순 로그, 시간대와 시간창 경계, 25,000건의 로그도 점검했습니다.

결과

유효한 행은 분석하고 잘못된 줄은 별도로 보고하도록 구성했습니다. 입력 형식별 결과가 같은지, 대량 파일의 끝부분에 있는 반복 오류도 탐지되는지 확인했습니다.

APP / EXECUTION

분석 결과에서
실제 근거를 확인할 수 있습니다.

결과 행을 선택하면 오류가 집중된 시간, 반복 횟수와 기준, 요청 경로를 상세 영역에서 확인할 수 있습니다. 아래는 25,000건 예제 로그의 끝부분에 있는 서버 오류를 확인한 실행 기록입니다.
