HTTP Status Pattern Analyzer.

반복 오류의 유형을 나눠, 불필요한 경보를 줄이는 기준을 찾았습니다.

웹 로그에 4xx나 5xx 응답이 많다고 해서 모두 같은 문제라고 볼 수는 없습니다. 저는 초기에 오류를 하나의 기준으로 묶어 분석했지만, 그 방식으로는 어떤 Host/IP를 먼저 확인해야 할지 충분히 설명할 수 없다는 점을 발견했습니다. 그래서 4개 오류 유형의 시간창·횟수 기준 48개 조건을 비교하고, 선택한 기준을 Windows 로그 분석 앱의 기본 규칙에 반영했습니다. 기존 실험 결과를 재집계해 공통 기준과 유형별 기준의 차이도 확인했습니다.

Python · 실험 분석C# · Windows Forms슬라이딩 시간창모의실험 48조건CSV · JSON
48 CONDITIONS · 4 STATUS GROUPS

같은 오류, 다른 판단 기준.

01 / WHY THIS PROJECT

먼저, 무엇이 불편하거나
잘못됐는지 생각했습니다.

한꺼번에 발생한 HTTP 오류를 단순 집계하면, 인증 실패와 없는 페이지 요청, 요청 제한, 서버 장애가 모두 같은 무게로 취급됩니다. 숫자만 보여주는 도구라면 분석에 익숙하지 않은 사용자는 결국 원본 로그를 다시 읽어야 했습니다.

02 / PROBLEM SOLVING

만들면서 마주친 문제를
이렇게 해결했습니다.

기능을 나열하는 대신, 처음의 생각과 수정한 이유, 그 결과를 순서대로 기록했습니다.

CASE 01 PROBLEM → CHANGE → RESULT

4xx를 한 그룹으로 묶었던 첫 실험을 바꾸다

어떤 점이 문제였나

처음에는 4xx 전체에 하나의 반복 횟수와 시간 기준을 적용했습니다. 하지만 401/403, 404, 429는 의미와 발생 패턴이 다릅니다.

이렇게 바꿨습니다

401/403·404·429·5xx 네 범주로 나눈 뒤 30·60·120초의 시간창과 3·5·8·12회의 기준을 조합해 총 48개 조건을 비교했습니다.

결과와 의미

유형별로 F1이 높은 조건이 달랐습니다. 같은 모의 데이터의 공통 기준과 비교하면 오탐은 117건에서 25건으로 줄었고, 탐지된 이상 사례도 756건에서 745건으로 줄었습니다. 두 결과를 함께 보고 유형별 기준을 앱의 기본 규칙으로 연결했습니다.

CASE 02 PROBLEM → CHANGE → RESULT

‘몇 번 발생했나’보다 ‘왜 확인해야 하나’를 먼저 보여주다

어떤 점이 문제였나

초기 화면은 Host/IP와 숫자, 임계값이 먼저 보여 사용자가 탐지 이유를 바로 이해하기 어려웠습니다.

이렇게 바꿨습니다

어느 경로에서 무슨 오류가 몇 초 안에 몇 번 반복됐는지 문장으로 설명하고, 판단 근거가 된 로그와 주요 경로를 함께 보여주는 형태로 결과 화면을 수정했습니다.

결과와 의미

로그를 처음부터 모두 읽지 않아도 우선 확인 대상을 좁히고 근거를 따라갈 수 있는 흐름을 만들었습니다.

CASE 03 PROBLEM → CHANGE → RESULT

입력 데이터가 매번 깔끔하지 않다는 점을 고려하다

어떤 점이 문제였나

실제 분석 대상은 형식이 섞이거나 일부 행이 손상될 수 있습니다. 올바른 예제 한 개로만 확인해서는 도구를 신뢰하기 어렵다고 봤습니다.

이렇게 바꿨습니다

Nginx/Apache 로그와 CSV·JSON/JSONL 입력을 처리하도록 구성하고, 잘못된 줄이 섞인 예제와 대량 로그 예제로 결과를 점검했습니다.

결과와 의미

유효한 행의 분석과 잘못된 입력 보고를 구분해, 문제를 발견하기 쉬운 처리 흐름을 만들었습니다.
