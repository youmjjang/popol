GIGANG.

개별 이벤트를 보는 것을 넘어, 왜 위험한 사건인지 설명할 수 있게 만들었습니다.

사내 자료 조회, 브라우저 AI 서비스 접근, 붙여넣기와 파일 첨부 시도가 서로 다른 로그로 남으면 위험의 전후 관계를 놓치기 쉽습니다. GIGANG은 이를 하나의 관제 흐름으로 연결한 팀 프로젝트입니다. 팀에서 이벤트 수집, 서버·단말 연동, 위험도 분석과 정책 대응을 연결했습니다. 실제 이벤트의 관제 반영 기록과, 별도로 구성한 오프라인 판정 시나리오의 결과를 구분해 정리했습니다.

PythonFlask · PostgreSQLStreamlit · RailwayJavaScript · Chrome Extension MV3SQLiteRisk ScoringGemini 보조 분석

팀 구현과 개인 기여

팀 구현 · 브라우저·단말·DB 이벤트 수집, 중앙 API, 위험도 분석, 관제와 정책 대응.

개인 기여 · 브라우저 입력·첨부 전 검사와 안내 화면 개선, 사이트 차단 정책 갱신 지연 개선에 참여했습니다. AI 코딩 도구를 활용했으며 변경 내역은 커밋으로 남겼습니다.

CASE 02 PROBLEM → CHANGE → RESULT

고정 점수 대신 ‘어떤 자료였는가’를 반영하다

어떤 점이 문제였나

복사·캡처·다운로드나 외부 입력에 고정된 위험 점수를 주면 자료 민감도와 실제 연관성이 달라도 같은 위험으로 표시되는 문제가 있었습니다.

이렇게 바꿨습니다

팀 판정 로직에는 부서별 정책, 민감정보 유형과 건수, 원본 자료 지문 일치 여부, 현재 WATCH 상태 등을 반영했습니다. 사건별 점수와 사용자 요약 점수를 분리하고 중복 가산도 막도록 보완했습니다.

결과와 의미

NORMAL·WATCH·HIGH 상태뿐 아니라 ‘왜 이 점수가 나왔는지’ 근거를 사건 단위로 남길 수 있게 했습니다.

CASE 03 PROBLEM → CHANGE → RESULT

목업 화면이 아니라 실제 수집 이벤트로 검증하다

어떤 점이 문제였나

디자인이 완성돼 있어도 고정된 예시 데이터로만 화면이 채워진다면, 실제 서버 수신·판단·대응이 이어지는지 알 수 없습니다.

이렇게 바꿨습니다

Railway와 로컬 에이전트에서 들어온 로그가 관제 화면에 반영되도록 연결하고, 화면의 사건 목록·심각도·정책 상태를 확인했습니다. 사이트 접근 차단과 자료 유출 차단을 구분하는 정책 제어 흐름도 연결했습니다.

결과와 의미

직접 진행한 테스트에서 이벤트 수신, 상태 분류, 케이스 반영 등 연동 결과를 확인했습니다. 화면 수치는 시험 시점의 데이터로 기록했습니다.

사이트 차단 갱신 지연 개선

이미 열린 탭의 정책 확인이 30초 알람 중심이었던 구조에 1초 간격 확인 요청을 추가했습니다. 여러 탭의 중복 정책 요청을 합치고 탭별 확인을 병렬화했습니다. 브라우저의 백그라운드 타이머 제한과 서버·권한 조회 지연이 있어, 실제 차단 시간의 개선 폭은 별도 측정이 필요합니다.

실제 이벤트 연동 기록은 별도로 남겼습니다

아래 관제·파이프라인 캡처는 시험 당시 이벤트 수신과 화면 반영 상태를 보여주는 기록입니다. 화면에 표시된 수집량과 분류 건수는 탐지 성능 지표로 사용하지 않았습니다.
