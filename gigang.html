CASE 01 PROBLEM → CHANGE → RESULT

형식이 다른 로그에서 분석에 필요한 값을 복원했습니다.

문제

서버에 저장된 raw_data에는 JSON 문자열뿐 아니라 작은따옴표를 사용하는 Python 딕셔너리 표현 문자열도 있었습니다. JSON 파싱만 하면 해당 값을 읽지 못하고, 검사 결과나 자료 출처가 분석 단계에서 빠질 수 있었습니다.

처리 과정과 선택

먼저 json.loads로 해석하고 실패하면 ast.literal_eval로 리터럴 값을 읽는 기존 파서 흐름을 활용했습니다. 날짜·행동 유형·사용자·PC·IP를 공통 SecurityEvent 구조로 맞추고, raw_data 안의 검사·출처 메타데이터를 복원해 판정에 전달하도록 보완했습니다. 같은 이벤트 ID를 다시 분석하지 않는 처리도 연결했습니다.

결과·근거

자료가 서버에 도착했는지뿐 아니라 분석에 필요한 필드가 끝까지 유지되는지 확인할 수 있도록 했습니다. 로그를 공통 구조로 바꿔 중앙 수집 기록과 DB 접근 기록을 같은 분석 흐름에서 다루도록 연결했습니다.

CASE 02 PROBLEM → CHANGE → RESULT

같은 이름의 PC 기록이 합쳐져 보이는 문제를 구분했습니다.

문제

다른 PC에서 전송에 성공했는데 관제에는 한 PC만 보이는 문제가 있었습니다. PC 이름이 같았고, 복제된 Windows 환경에서는 MachineGuid 기반 기기 ID까지 같아질 수 있었습니다. 단순 전송 실패와 화면 집계 오류를 나눠 확인해야 했습니다.

처리 과정과 선택

최초 실행 시 PC별 UUID를 생성해 로컬 상태 파일에 저장하고 재실행 후에도 유지하도록 바꿨습니다. UUID 파일을 실행 패키지에 포함하지 않아 다른 PC에 복사되지 않게 했습니다. 관제 집계에서는 기기 ID·PC 이름·IP 조합과 충돌 여부를 함께 확인하도록 개선했습니다.

결과·근거

당시 기기 식별 관련 기본 테스트 7개 통과 기록과 PC가 분리돼 표시된 사용자 확인이 남아 있습니다. 별도 집계 테스트에는 같은 이름·복제 ID·서로 다른 IP 3개를 3개 그룹으로 나누는 사례가 있습니다. 실제 PC 7대나 3대의 성능 시험 수치는 아닙니다.

CASE 03 PROBLEM → CHANGE → RESULT

텍스트·파일·스크린샷을 서로 다른 방식으로 비교했습니다.

문제

글자 수나 파일 이름만 같다고 회사 자료와 같은 내용이라고 볼 수 없었습니다. 이미지는 파일 해시가 달라져도 같은 자료를 담을 수 있어, 텍스트·파일의 정확 일치와 별도의 검사 방식이 필요했습니다.

처리 과정과 선택

텍스트는 줄바꿈을 통일한 뒤 세션 seed를 포함한 SHA-256 지문으로 비교하고, 파일은 바이트의 SHA-256을 비교했습니다. 이미지는 Windows OCR로 글자를 추출하고 정규화한 뒤 회사 표의 셀 지문과 대조했습니다. 검사·일치·출처 메타데이터가 중앙 분석에 전달되도록 보완했습니다.

결과·근거

파일명·크기 같은 약한 연관성과 내용 일치를 구분할 근거를 연결했습니다. OCR 비교는 같은 행의 유효 필드 3개 이상 일치 또는 strong으로 분류한 숫자 필드 일치를 기준으로 삼았습니다. OCR 실패·기준 자료 없음은 내용 일치 차단과 구분해 보류 처리했습니다.

CASE 04 PROBLEM → CHANGE → RESULT

WATCH 상태와 약한 연관성만으로 HIGH가 되는 흐름을 바꿨습니다.

문제

과거 판정에서는 현재 WATCH 상태나 과거 감시 이력, 파일 이름·크기 같은 근거가 HIGH 승격으로 이어질 수 있었습니다. 단순한 행동의 연결과 실제 자료 내용 일치를 구분할 필요가 있었습니다.

수정 과정과 선택

위험 등급을 일괄적으로 낮추기보다 자료 연결 근거를 나눴습니다. 팀 판정 로직에서 글자 수 유사성, 파일 이름·크기 일치, 원본 내용 일치를 구분하고 목적지 승인 여부와 민감정보 종류·건수를 함께 반영했습니다. 사건별 점수와 사용자 위험 요약도 분리했습니다.

결과

동일한 오프라인 시나리오를 두 버전에 입력한 비교에서 승인 목적지·약한 연관성 등 비교 사례의 불필요한 HIGH 분류는 4건에서 0건으로 줄었습니다. 내용 일치가 주어진 미승인 외부 입력·첨부 10건은 두 버전 모두 HIGH로 분류했습니다.

CASE 05 PROBLEM → CHANGE → RESULT

붙여넣기·첨부 시도를 전송 완료로 해석하지 않도록 했습니다.

문제

브라우저에서 붙여넣기나 첨부를 감지해도 사용자가 실제 전송 버튼을 눌렀는지, 자료가 외부에 도착했는지까지 확인되는 것은 아니었습니다. 전송 전에 막은 사건까지 유출 완료처럼 기록하면 대응 근거가 부정확해질 수 있었습니다.

수정 과정과 선택

판정 등급과 전송 상태를 구분했습니다. 사건 설명에 입력·첨부 시도, 전송 전 차단, 전송 관측을 나눠 기록하도록 보완했습니다. 전송이 관측된 경우에도 민감자료의 전송 완료까지 확인된 것으로 단정하지 않았습니다.

결과

HIGH 등급과 실제 전송 완료를 같은 의미로 사용하지 않도록 했습니다. 관제 화면에서 어떤 행동이 관측됐고 차단 결과가 무엇인지 근거를 확인할 수 있도록 사건 설명을 정리했습니다.

CASE 06 PROBLEM → CHANGE → RESULT

이미 열린 사이트의 차단 정책 반영이 늦는 문제를 개선했습니다.

문제

전면 차단 정책을 변경해도 이미 열린 탭은 다음 정책 확인까지 기다려야 했습니다. 기존 확장은 30초 알람 중심으로 갱신했고, 여러 탭을 확인할 때 순서대로 권한 응답을 기다리는 구조였습니다.

수정 과정과 선택

열린 탭에서 1초 간격으로 정책 확인을 요청하도록 보완했습니다. 여러 탭이 동시에 요청할 때는 진행 중인 정책 조회를 공유하고, 탭별 확인은 병렬로 처리하도록 바꿨습니다. 탭이 없는 상황에 대비한 기존 알람 방식도 유지했습니다.

결과

정책 확인을 30초 알람에만 의존하던 구조에서 열린 탭이 갱신을 요청하는 구조로 바꿨습니다. 1초는 확인 요청 간격이며, 실제 차단 시간은 서버·권한 응답과 브라우저의 백그라운드 실행 제한에 영향을 받습니다.
